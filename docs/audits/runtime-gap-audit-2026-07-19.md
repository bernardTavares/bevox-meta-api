## Parte B — Os 2 CRÍTICOS + o A5b (bloqueiam piloto) — lidos em primeira mão

**A5 — dedup `SET NX` reivindica a chave ANTES de persistir o `InboundEvent`; `meta_event_id` sem `uniqueIndex`; sem `del()` compensatório → perda silenciosa e permanente de inbound em qualquer blip de Postgres** · SURVIVES · **[orq — leitura direta]**
- Ev.: `src/modules/inbound/service.ts:298` chama `isDuplicate()` (SET NX EX 24h, def. `:184-194`) **antes** de `insertInboundEvent()` em `:324`. Nenhum `del()` compensatório no arquivo. `db/schema/operations.ts:98` usa `index("inbound_events_meta_event_id_idx")` — **não-único** — enquanto `uniqueIndex` está importado e usado logo acima (`:68`, `outbound_jobs_app_idempotency_uniq`): a escolha é deliberada. Única migration é `0000_initial_schema.sql` (nenhuma nova). Logo o `SET NX` no Redis é o **único** dedup.
- Falha: insert lança (blip de DB/pool/failover CNPG) → 500 → Meta retenta → `isDuplicate` retorna `true` (chave já setada) → conta `deduplicated` → **200 OK** → evento **nunca persistido nem entregue**. **Esforço do fix ingênuo: ~4h** — mas ver A5b: insuficiente sozinho.

**A5b (NET-NEW, ALTO) — enqueue não-atômico após o `SET NX`: mesmo com insert bem-sucedido, um blip nos passos seguintes deixa o evento persistido mas PERMANENTEMENTE sem entrega** · NEW · verify CONFIRMED (webhook-hmac-auditor + orq)
- Ev.: em `inbound/service.ts`, os efeitos colaterais best-effort **estão** guardados em try/catch — `disconnectWaba` (`:346-358`), media-enqueue (`:362-372`), `publishEvent` (`:375-386`). Mas `listActiveSubscriptions(...)` (`:388`) e o loop `queue.add(...)` (`:402-410`) **NÃO estão**. Se qualquer um lançar (blip de Redis/pool BullMQ, blip de Postgres na listagem de subscriptions), `processSingle` lança → 500 → Meta retenta → o `SET NX` já reivindicado em `:298` faz `isDuplicate=true` → **200 OK** → as deliveries daquele evento nunca (re)enfileiram. Se lançar no meio do loop, as subs já processadas ficam enfileiradas e o resto fica **permanentemente sem entrega**; o `jobId` idempotente `${sub.id}:${event.id}` (`:409`) nunca tem chance porque o dedup suprime o reprocessamento.
- **Por que importa:** prova que **`uniqueIndex` em `meta_event_id` sozinho NÃO fecha o A5** — ele resolve "insert falha" mas não "enqueue falha após insert commitado" (um retry bateria na unique constraint e ainda pularia o enqueue). O fix correto: no caminho de duplicata, **re-dirigir idempotentemente** o persist+enqueue (o `jobId` do BullMQ já é idempotente, então re-enfileirar é seguro), ou confirmar a chave de dedup só após persist+enqueue completos. **Esforço combinado A5+A5b: ~6h.** Bloqueador #1 do piloto, agora com escopo correto.

2. **F1 — retry da fila async é auto-envenenado: o row `failed` (tentativa 1) colide com o row `sent` (tentativa 2) na idempotency-key reusada → mensagem ENTREGUE reportada como `failed`, callback `failed`, consumer reenvia** · verify CONFIRMED (crítico net-new + **orq leitura direta**)
   - Ev.: `outbound-dispatcher.ts:105` chama `sendMessage({ idempotencyKey: `async:${job_id}` })` — key **estável entre retries**. Em `messages/service.ts`, o caminho de falha (`:186-201`) faz `insertOutboundJob({ status:"failed", idempotencyKey:"async:<jobid>" })` **e re-lança**; o caminho de sucesso (`:203-214`) faz `insertOutboundJob({ status:"sent", idempotencyKey:"async:<jobid>" })`. `insertOutboundJob` não tem `onConflictDoNothing` (`messages/repository.ts:87-105`) e há unique `(app_id, idempotency_key)` (`operations.ts:68`).
   - Sequência (caso comum — **timeout após a Meta receber**): tentativa 1 → Meta **recebe** mas a resposta dá timeout → `META_UNAVAILABLE` (retryable) → insere row `failed` → re-lança → dispatcher marca `queued` e re-lança (`:127-135`) → BullMQ agenda tentativa 2. Tentativa 2 → Meta **reenvia** (envio dobrado) e aceita → tenta insert `sent` (mesma key) → **violação de unique** → o erro sobe **FORA** do try/catch de `sendMessage` (que terminou em `:201`) → dispatcher captura em `:121` → `INTERNAL` **não-retryable** (`:123-131`) → grava `failed` + dispara **callback `failed`** (`:138-148`).
   - Impacto: (a) a mensagem foi entregue (potencialmente 2×), mas `GET /v1/jobs/:id` reporta `failed` e o consumer recebe callback `failed` → **reenvia → 3ª entrega**; (b) variante: se a tentativa 2 também falha na Meta, o insert `failed` **também** colide → morre como `INTERNAL` antes das tentativas 3-5 → **o retry async fica quebrado após a 1ª falha transitória**. Distinto da corrida de idempotência do corpus (concorrência HTTP) e de rlq-2 (429 terminal): a raiz aqui é o **row `failed` envenenando a key reusada no worker async** (0% de teste). **~3h** (`onConflictDoUpdate` na key async, ou não persistir `failed` com a key reusada, ou UPDATE do row `queued` existente em vez de novo insert).

3. **F2 — `pool.on("error")` do Postgres é um footgun: engole falha de failover nos workers, mas DERRUBA a API-com-Sentry sem drain — e o "propagar ao shutdown handler" prometido nunca acontece** · verify CONFIRMED (crítico net-new + **orq leitura direta**)
   - Ev.: `db/client.ts:51-53` — `pool.on("error", (err) => { process.emit("uncaughtException", err); })`. **Não existe listener `uncaughtException` no app** (grep `src/` = só `unhandledRejection` em `index.ts:38`). `process.emit("uncaughtException", err)` sem listener é **no-op** (verificado empiricamente em Node v22.23.1, exit 0). Em prod a API roda `initTelemetry()` (`index.ts:23`) → `Sentry.init` com integrations default (`telemetry.ts:52-66`, sem `defaultIntegrations:false`) → a integração `onUncaughtException` do Sentry FICA ativa → captura e **termina o processo**. Os workers **não** chamam `initTelemetry` (blocos `isMain`) → neles é sempre no-op/swallow.
   - Impacto: um `'error'` de cliente pg ocioso é **rotineiro** (failover do CNPG single-instance/infra-4, kill de conexão ociosa, blip de rede) e dispara para vários clientes de uma vez. O comentário `:49-50` afirma "propagar para shutdown handler decidir" — **falso** (hooks de shutdown só em SIGTERM/SIGINT, `shutdown.ts:100-101`). Resultado: **(a)** workers + API-sem-Sentry → erro **invisível** (sem log/métrica/recuperação), mascarando instabilidade de DB; **(b)** API-com-Sentry (prod) → **crash duro sem drain** (requests in-flight cortados, `/readyz` nunca vira 503, sem LIFO — compõe com a ordenação invertida de shutdown, item (d) do 07-17). Divergência teste↔prod: em CI (sem Sentry) o caminho é no-op → **o comportamento real de prod nunca é exercitado**. **~2h** (handler que loga + métrica + sinaliza readiness-drain em vez de `process.emit`).
